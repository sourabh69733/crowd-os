# Freegram Android slice: status

Updated 26 September 2026. This is a developer prototype, not a field pilot or a release candidate.

## Implemented and verified

- `apps/android` builds a debug APK with Kotlin and Compose. `:app:testDebugUnitTest` and `:app:assembleDebug` passed locally.
- NIP-01 canonical serialization matches both portable fixtures in `protocol/vectors/nip01-id-v1.json`, including Unicode and newline content. The test suite runs official [BIP-340 vectors 0–14](https://github.com/bitcoin/bips/blob/master/bip-0340/test-vectors.csv), which cover 32-byte messages used for Nostr IDs. Modified message, signature, public key and over-limit content are rejected by tests. BIP-340 vectors 15–18 use other message lengths and are outside this Nostr event-ID path.
- [ACINQ secp256k1-kmp 0.24.0](https://github.com/ACINQ/secp256k1-kmp) supplies the Schnorr implementation and is published under Apache-2.0. A candidate NDK Kotlin `1.0.0` artifact was not found on Maven Central; current Quartz `1.16.0` required Android API 37 / AGP 9.1 through its dependencies, while the installed SDK is API 36. Those packages were not adopted.
- The prototype saves a draft and signed bulletin locally before network submission. It records each relay's `OK` acceptance/rejection independently and retains a pending bulletin for manual retry after restart. `Accepted` is an observed relay response, never a global delivery claim.
- Room 2.8.5 stores drafts, signed events, per-relay delivery records and author controls. Event and relay-target inserts share a transaction. Tests cover restart persistence, invalid signatures, the 100-event limit, and both old SharedPreferences migration and Room version 1 → 2 migration. The target phone retained its saved posts across the version-2 update.
- The bridge test screen now copies a signed public event, verifies and queues an imported event without the carrier's signing key, and fetches one event ID from either relay. A fetched event is verified before local storage and is not queued for forwarding until the user explicitly imports it as a carrier. A local TLS WebSocket test passes the unchanged signed event from a carrier client to a reader client. This is an app/protocol integration test, not a physical-device test.
- Automatic relay retry: each relay gets up to three attempts (2 s and 5 s apart) for temporary failures only: network error, timeout, HTTP 5xx/429 and `rate-limited` rejections. Other rejections are final. Remaining temporary failures go to a WorkManager job that needs a network connection, uses exponential backoff from 30 s, stops after 10 runs, and skips events older than 48 hours. Only relays the user already asked to submit to (`Sending` or a failure) are retried; an imported carried event stays `Pending` until explicit submit. A stored `Accepted` is never replaced by a later failure. Handshake failures now show the HTTP code (e.g. `HTTP 503`). Tests cover retry to acceptance, bounded attempts, non-retried rejections, the no-downgrade rule, age and `Pending` exclusion.
- Full store (100 posts): instead of refusing every new post, the store removes one post to make room. Order: posts by blocked authors, then the oldest received post, then the oldest own/carried post that every relay accepted. A post still waiting on any relay (including an imported carried post not yet submitted) is never removed; if all 100 are waiting, new posts are refused with a clear message. A received post older than everything removable is not kept, so stale fetches cannot push out newer posts; the feed reports how many were skipped. Unit tests cover each rule; this was not exercised on a phone with 100 stored posts.
- Per-author cap: at most 20 received posts are kept per author (from relays or nearby); a newer one replaces that author's oldest, an older one is not kept. Posts this phone submitted to relays are not capped. This stops one key from filling the store, but many cheap keys still can (see the threat model).
- Feed catch-up: after a completed refresh, each relay remembers the newest post time it returned. The next refresh asks only for posts since then (minus 10 minutes for clock skew) and pages back up to 3 batches of 50; if more were missed, the result says the oldest were skipped. A failed relay keeps its old mark; following or changing any author resets all marks so the new author's history is fetched. Tests use a fake relay that honours `since`/`until`/`limit`; this was not checked against live relays.
- Room returns saved, verified bulletins in newest-first order. The app lists local copies and can reopen older entries. A storage test covers order, deduplication and reopening; an older entry opened on the target phone.
- A manual followed-author feed queries up to 20 keys and 50 recent `kind:1` events per relay. The app verifies author, ID, signature, size and future timestamp before storage, limits incoming frames, deduplicates by event ID, and reports each relay separately. Local mute hides a key from feed/refresh; block also rejects new storage and hides saved copies without deleting them. The UI labels sources and reports as unverified. Local TLS and storage tests cover the path; this is not background sync or global discovery.
- An Android Keystore AES-GCM key wraps the exportable Nostr secret at rest. This does **not** make BIP-340 signing hardware-backed: the secret is decrypted into app memory while signing. Android backup is disabled for this prototype.
- Key backup and recovery: the identity section shows the public key as NIP-19 `npub` and hex, reveals the secret as a NIP-19 `nsec` only on request, and blocks screenshots (`FLAG_SECURE`) while it is visible. The secret is never copied to the clipboard. A user can restore an `nsec` on another install, or replace a suspected-compromised key with a new random one. Both need a second confirmation; an invalid backup leaves the current key unchanged. Nostr has no revocation, so a stolen old key can still sign valid posts; the UI tells users to announce a new key through a channel followers already trust. The follow field accepts `npub` or hex. Tests cover the official NIP-19 `npub`/`nsec` examples, checksum/prefix/case rejection, restore on a second store, invalid restore, and replacement. Recovery depends entirely on the user keeping the `nsec` safe; there is no encrypted (NIP-49) backup or social recovery.

- Nearby exchange logic (Phase 3 preparation): a transport-independent session implements the Phase 0 exchange (`HELLO` → recent-ID `HAVE` ≤128 → `WANT` ≤32 → `EVENT`… `SENT` → `ACK`/`NACK`), specified in [protocol/README.md](../../protocol/README.md). Room schema version 3 adds an unsigned per-copy hop count; existing posts migrate with 0. In-memory tests cover A → B → C with no A–C contact (C verifies A's unchanged event at hop 2), two-way swap, skipping held posts, tampered, unrequested, duplicate, too-old, future, over-hop and blocked-author events, bounded inventory and transfer (40 posts need two exchanges), requests for unoffered IDs, disconnect, timeout, malformed and oversized frames. No radio adapter, discovery, per-peer rate limit, battery or device test exists yet; Nearby Connections must be added behind `PeerLink` on physical phones.

- Nearby Connections adapter (`play-services-nearby` 19.3.0, `P2P_CLUSTER`): an explicit **Share nearby** mode, only while the screen is open, advertises and discovers under a random per-session name (`fg-xxxxxx`), never the signing key. Connections are accepted without a pairing code because posts are public and signature-checked; a nearby attacker can therefore connect, which the exchange limits bound. Each connection runs one exchange, waits up to 5 s for pending frames, then disconnects. A per-name limit (one exchange per 60 s) and a cap of 3 concurrent exchanges apply; renamed peers evade the per-name part. Wrong-type, oversized or flooding payloads disconnect the peer. The screen shows each exchange's received/rejected/sent/confirmed counts. On the Pixel 9a emulator the mode started (Nearby service accepted the client, advertised as `fg-d4ae2e`) and stopped without an app crash; the emulator has no usable radio, so no exchange was attempted. Open device questions: whether BYTES payloads always arrive in order (the exchange fails safely if not), discovery time, battery, locked-screen behavior, and phones without Google Play services (the mode is disabled there).
- Offline-to-internet bridge (Phase 4, decided 27 September: automatic): when **Publish posts received nearby** is on (default), each post received nearby is queued (`Sending`) for both configured relays in the same transaction that stores it, and the background retry job publishes the unchanged signed event once the phone is online. The switch warns that relays see the carrier's IP address. Queued nearby posts count as someone else's posts for storage limits, so they cannot fill the store and block the user's own posts. A simulated A (offline) → nearby → B → relay → reader D test passes with A's exact event and signature; relay rejections are final. Not yet run on phones.
- Nearby photo sharing (Phase 5 start, P2P-first): a post may carry one photo, re-encoded on the phone as JPEG (at most 1600 px, 1 MiB) so EXIF metadata such as GPS is not copied. The post references it by SHA-256 in a NIP-92 `imeta` tag without a URL; any source can supply the bytes and the receiver checks the hash before storing. After the text round, phones that both support photos swap up to 8 missing photos per exchange in 16 KiB chunks (BLOBHAVE → BLOBWANT → BLOB/CHUNK → BLOBACK), offering only photos of posts they would share anyway. Photos are capped at 50 MB per phone; unreferenced photos go first. A phone without photo support still swaps text. Tests cover two-hop photo travel, photo arriving later from another phone, altered, unrequested, out-of-order, oversized and cut-off transfers, blocked authors, and the storage cap. **Not yet run on a device**: the JPEG re-encoding and metadata removal, the photo picker, and Nearby payload sizes. Photo posts sent to relays carry the hash but not the photo, so internet-only readers cannot see it until media hosts exist.
- Screen state and actions moved into a ViewModel (`FreegramViewModel`); inputs survive rotation.

## External integration results

- A throwaway BIP-340 key produced the exact official vector-0 signature with an independent `coincurve` probe.
- A 25 September probe to `wss://relay.damus.io` and `wss://nos.lol` stopped at HTTP 503/502 handshakes. On 26 September, the same independent-client probe succeeded: both relays returned `OK true` for throwaway event `d89115c8d9e8645fb771f81f32ba0777234391aa54664b9b9d713c49ceffa46d`, and a separate connection fetched it from each. The relays' [Damus](https://relay.damus.io/) and [nos.lol](https://nos.lol/) NIP-11 responses report different names and public keys. This verifies current acceptance and retrieval of a carrier-submitted event from this computer; it does not prove operator independence, retention, phone behavior or offline delivery.
- On 26 September, a `CPH2569` Android phone ran the debug app. For one harmless signed bulletin, its UI showed `Accepted` from both configured relays. Fetching the same event ID through the app succeeded from `wss://nos.lol`; the first `wss://relay.damus.io` fetch returned `Network error`, then a retry fetched and verified the event. After force-stop and restart, the same event ID and both `Accepted` states were visible. This is one phone and one event, not a cross-device or reliability result. The exact cause of the transient network error is unknown.
- On the same phone, following the public test key and refreshing returned two verified posts from `wss://nos.lol`, with no duplicates in the local feed. Mute hid both and unmute restored them. `wss://relay.damus.io` returned `Network error` on two author-feed refresh attempts. After reinstalling the updated build, one more refresh completed from both relays: Damus returned one verified event and nos.lol returned two, with two unique saved posts. The cause of the earlier failures remains unknown. This does not establish second-device delivery or reliable relay service.
- A Pixel 9a emulator was installed as a separate Freegram device. After following the physical phone's public key, it fetched three verified posts through the relays; its saved list included the phone's exact event ID `7e72e48a28ccec0175de5bd2d981e9dd15ca05c9f7b97bede7e614f2c8d67b4f`. An author-feed refresh completed from Damus (one event) and nos.lol (three events). With Damus replaced by an unreachable local endpoint, nos.lol still completed with three events; with nos.lol replaced, Damus completed with one. Both original relay URLs were restored afterward. This validates a phone-to-emulator internet read and one-relay-outage behavior, not two-physical-phone delivery or relay uptime.
- On 26 September, the key-backup build was installed over the previous build on the `CPH2569` phone. It kept its existing key (`c1a969c0…`, the author of its earlier posts). On the Pixel 9a emulator, with the real Android Keystore wrapper: the secret backup was revealed (screen capture returned a black frame), the key was replaced with a new one, then the backup was restored; the original public key returned and survived force-stop/restart. The Android accessibility tree can still read the revealed text, so an accessibility-enabled malicious app could capture it. Backup was not tested between two physical phones.
- Restart during delivery, 26 September, `CPH2569`: a harmless bulletin (`54b2552b5c6b5ab39379a4588954eebf4095b61fa66c057d574304dab947c5cb`) was sent and the app force-stopped 0.3 s after the tap. After restart the same event ID was shown, the draft was cleared, and both relays read `Pending`: no false delivery. The first manual retry got `Accepted` from nos.lol and `Network error` from Damus; after another restart both states were unchanged. The next retry skipped nos.lol and got `Accepted` from Damus. One copy was listed. An independent client then fetched the event from both relays. Six back-to-back Damus probes from this computer returned HTTP 503 on the WebSocket handshake twice and found the event four times, so the earlier intermittent Damus `Network error` results match server-side 503 rejections, not an app fault. This is one kill point on one phone; a kill after one relay's `OK` but before the database write was not isolated.
- Background retry, 26 September, `CPH2569`: with Wi-Fi and mobile data off, a harmless bulletin (`3c5edcccdd216f49a82a9ddf659f108875c377be35b9e4426fe9ba15d0f3ed85`) showed `Network error · will retry automatically when online` for both relays. The app was sent to the background and its process killed (`am kill`), then the network was restored without opening the app. Android started the process and ran the retry job about 1 s later; it finished about 5 s after reconnecting, the app then showed `Accepted` for both relays, and an independent client found the event on both. After an explicit **force-stop**, Android runs no background work for the app until the user opens it again; the job then runs from app start. Reboot and long Doze delays were not tested. Duplicate job runs can occur (three here) but only the first had work.
- On 26 September the build with Room schema 3, the ViewModel and Share nearby was installed over the previous build on the `CPH2569` phone. It started without an app error, showed the latest saved post, and kept the same signing key (`c1a969c0…`).
- No second physical Android phone is available yet. Nearby A → B → C, carrier bridging on devices, battery, Google Play services dependency and background behavior remain untested.
